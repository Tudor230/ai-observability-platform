
# 5. KPIs & Success Criteria

## 5.1 Objective

The objective of this section is to define how the proposed Agentic Observability and FinOps Platform will be evaluated.

The project will be evaluated based on whether it can reliably provide the observability and cost information defined in:

- [03 — Proposed Solution / TO-BE Flow](./03-to-be-solution.md)
- [04 — High-Level Architecture](./04-high-level-architecture.md)

This section therefore focuses only on **how success will be measured**, rather than repeating the solution or architecture.

## 5.2 Primary KPI 1 — Observability Coverage

### Definition

Measure whether the platform captures the relevant execution information defined in the proposed solution.

The test will compare the operations intentionally executed by a controlled agentic workflow with the telemetry available in the platform.

### Measurement

```text
Expected execution steps
          |
          v
     Test workflow
          |
          v
Captured telemetry
          |
          v
    Compare results
````

The measurement will use:

```text
Observability Coverage (%)
=
Captured Expected Events
------------------------- × 100
Total Expected Events
```

### Success Criterion

The platform successfully captures the relevant execution steps and metadata required by the observability model described in [03 — Proposed Solution / TO-BE Flow](./03-to-be-solution.md).

The final target value will be established during implementation testing.

## 5.3 Primary KPI 2 — Cost Attribution Accuracy

### Definition

Measure whether the platform correctly calculates the cost of an agentic execution and attributes it to the corresponding business context.

The calculation model is defined in [03 — Proposed Solution / TO-BE Flow](./03-to-be-solution.md) and the corresponding processing components are described in [04 — High-Level Architecture](./04-high-level-architecture.md).

### Measurement

A controlled test workflow will be executed with known:

* Model
* Input tokens
* Output tokens
* Pricing
* Number of calls
* Workflow
* Business identifier

The independently calculated expected cost will be compared with the cost generated by the platform.

```text
Known test parameters
        |
        +----> Independent calculation
        |
        +----> Platform calculation
                         |
                         v
                    Compare
```

The measurement will use:

```text
Cost Error (%)
=
|Expected Cost - Platform Cost|
-------------------------------- × 100
Expected Cost
```

### Success Criterion

The platform produces a cost value consistent with the configured pricing model and associates it with the correct workflow and business context.

## 5.4 Supporting Validation Criteria

The following are not primary KPIs, but will be checked during prototype validation:

| Area                 | Validation                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Integration          | A representative agentic application can be connected using the approach defined in [03](./03-to-be-solution.md). |
| Trace reconstruction | A complete test execution can be reconstructed from the captured telemetry.                                       |
| Business attribution | The execution can be associated with its configured business context.                                             |
| Cost calculation     | The cost engine produces the expected result for controlled test inputs.                                          |
| Dashboard            | The information required by the defined user views is available through the platform.                             |
| Alerts               | A predefined abnormal-consumption scenario triggers the expected alert.                                           |

## 5.5 Validation Method

A representative agentic workflow will be used as the evaluation scenario.

The workflow should contain enough operations to test the main capabilities described in the solution and architecture documents.

The evaluation process is:

```text
1. Define expected execution
          |
          v
2. Execute controlled workflow
          |
          v
3. Collect telemetry
          |
          v
4. Process telemetry
          |
          v
5. Calculate cost
          |
          v
6. Compare expected vs actual
          |
          v
7. Record KPI results
```

The test should be repeatable so that the same methodology can be used when additional agentic applications are integrated.

## 5.6 Overall Success Criteria

The prototype is considered successful if the validation demonstrates that:

* The observability integration works for a representative agentic application.
* The required telemetry can be captured and reconstructed into an execution trace.
* The platform can calculate execution cost from captured consumption data.
* The calculated cost can be attributed to the relevant business context.
* The resulting information can be exposed through the platform described in [04 — High-Level Architecture](./04-high-level-architecture.md).
* The defined KPIs provide an objective method for evaluating the solution.
